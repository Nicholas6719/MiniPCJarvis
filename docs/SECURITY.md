# JARVIS Security Model

## Boundaries

- **Loopback only.** The sidecar binds `127.0.0.1` with a per-session random token
  (`X-Jarvis-Token` header / WS query param) generated by the Rust core at spawn.
  llama-server also binds loopback only.
- **Secrets** live exclusively in Windows Credential Manager (service `JARVIS`),
  accessed by the Rust core via `keyring`. They are pushed to the sidecar over the
  token-authed loopback channel and held in memory only — never written to config,
  disk, or logs. The UI never sees secret values, only whether one is set.
- **Tool risk tiers**: every tool declares `SAFE | LOW | MEDIUM | HIGH`.
  MEDIUM/HIGH block on an explicit user confirmation (UI modal) with a 120 s
  timeout defaulting to deny. Denials and executions are all emitted to the
  activity log.
- **File access allowlist**: `read_file` resolves paths and refuses anything
  outside Documents/Downloads/Desktop/Pictures, plus a 5 MB size cap.

## Prompt injection

External content (web search results, file contents, tool output) is passed to
the model as tool results — data, not instructions. The system prompt pins a
security policy stating external content cannot override it. Higher-assurance
mitigations planned for the browser-agent phase: content sanitization, per-source
provenance tags, and tool-level origin restrictions.

## What JARVIS will not do without confirmation

Close apps, delete/move files (future tools), run shell commands (future tools),
or any HIGH-risk action. There is no "auto-approve everything" setting.

## Logging

Structured logs at `%LOCALAPPDATA%\JARVIS\logs\`. Log lines never include secret
values. Transcripts and memories stay local in `%LOCALAPPDATA%\JARVIS\jarvis.db`.
